Django 5 – Architecture & Project Structure

How Django works internally, server control, and professional project & app structure

This chapter explains how Django works internally, how to run and control the development server, and how projects and applications are structured in a professional Django workflow.

Understanding this chapter is critical before learning URLs, Views, Templates, and Models.

How to Run Django Development Server

The Django development server is a lightweight web server used only for development and testing purposes.

  1. Open terminal / command prompt
  2. Navigate to your Django project folder (where manage.py exists)
  3. Run the command:
python manage.py runserver

Default Server Address

By default, Django runs on: 

http://127.0.0.1:8000/
  • 127.0.0.1 → Localhost (your own computer)
  • 8000 → Default Django port
The site is accessible only on your system, not on the internet.

How to Change Django Server Port

Sometimes port 8000 may already be in use, or you may want to run multiple projects simultaneously. 

python manage.py runserver 8080

Server will now run at: 

http://127.0.0.1:8080/

How to Stop Django Server

To stop the development server safely: 

CTRL + C

Django Project vs Django Application

Django Project

  • The entire website or system
  • Contains settings, URLs, and configurations
  • Can include multiple apps

Examples:

  • College Management System
  • E-Commerce Website
  • Learning Management System

Django Application (App)

  • A specific module inside a project
  • Handles one responsibility

Examples:

  • Authentication app
  • Blog app
  • Student management app
  • Payment app
A single Django project can contain multiple apps, each handling a different feature.

Creating a Django Application (Professional Way)

Step 1: Go to Project Directory

cd sms

Step 2: Create Django App

python manage.py startapp app1

📘 Django Project Files – Explanation & Uses

When you create a Django project, Django automatically generates several important files. Each file has a specific role in running, configuring, and managing your application.

🔹 __init__.py

What it is:

  • An empty file
  • Marks the folder as a Python package

Why it is needed:

Allows Django and Python to import files from this directory.

🌍 Real-Life Example:
Like an ID card identifies a person, __init__.py tells Python: “This folder is a package.”

🔹 settings.py

What it is: The main configuration file of the Django project.

What it contains:

  • Installed apps
  • Database configuration
  • Middleware
  • Templates
  • Static & media files
  • Security settings
🌍 Real-Life Example:
settings.py is like the settings app of a mobile phone (Wi-Fi, display, security, apps).

🔹 urls.py

What it is: URL routing file.

What it does:

  • Maps browser URLs to views
  • Decides which logic runs for a given request
🌍 Real-Life Example:
If a user opens /login, urls.py decides which page or logic should run — like a road map directing traffic.

🔹 asgi.py

What it is: ASGI (Asynchronous Server Gateway Interface) configuration file.

Used for:

  • WebSockets
  • Chat applications
  • Live notifications
🌍 Real-Life Example:
Used in real-time apps like live chat systems and real-time dashboards.

🔹 wsgi.py

What it is: WSGI (Web Server Gateway Interface) configuration file.

Used for:

  • Connecting Django with servers like Apache, Nginx, Gunicorn
  • Production deployment
🌍 Real-Life Example:
Acts like a bridge between Django and the web server.

🔹 manage.py

What it is: A command-line utility to manage the Django project.

What it can do:

  • Start development server
  • Create apps
  • Apply migrations
  • Create superuser

Common Commands:

python manage.py runserver
python manage.py startapp appname
python manage.py makemigrations
python manage.py migrate
🌍 Real-Life Example:
manage.py is like a remote control for your Django project.

Registering Django App (Mandatory)

After creating an app, Django will not recognize it automatically. You must register it inside settings.py.

Without registering the app:
  • Models won’t migrate
  • Admin won’t show models
  • Views won’t work correctly

Django Architecture – Big Picture

  1. User sends request via browser
  2. URL matched in urls.py
  3. View processes the request
  4. Model interacts with database
  5. Template renders HTML
  6. Response sent back to user

This flow follows Django’s MVT (Model–View–Template) architecture.

Final Notes

  • Django server is for development only
  • Project = whole system, App = specific feature
  • Every app must be registered
  • Understanding architecture prevents confusion later
